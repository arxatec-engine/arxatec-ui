## `arxatec-ui@0.1.65` is published on npm and does not exist in git

> **Historical provenance unresolved** · registry `0.1.68`, base `main` `0.1.70`, Logo candidate `0.1.71`
> **Detected:** 2026-09-08 · **Last verified:** 2026-10-09 against base `main` (`563c36d`), `feat/logo-variants` and the npm registry

Original observations on 2026-09-08:

```bash
npm view arxatec-ui version      # 0.1.65
grep '"version"' package.json    # 0.1.64   (main, and every one of the 8 remote branches)
```

At detection, `arxatec-lawyer-platform` declared `arxatec-ui: ^0.1.65` and its `pnpm-lock.yaml`
is pinned to `0.1.65` with a real integrity hash, so the published tarball exists
and was in use. The old producing commit remains unidentified: a search of the available git
history still finds no `package.json` version `0.1.65`. This does not describe
the current package: registry remains on `0.1.68`, while base `main` prepares
`0.1.70` and the Logo variants candidate prepares `0.1.71`. Rechecking available
git history still finds no `package.json` version `0.1.65`.

Why it matters: this repo has no tests, and its only safety net is reading the
code and Storybook. A published version with no commit cannot be reviewed, cannot
be reverted by pointing at a tag, and cannot be diffed against what the consumer
is running.

The historical tarball provenance still needs investigation. For the next
release, review the diff from `a33d544` (`0.1.68`), including the prepared
`0.1.71` version bump in the Logo change, validate the packed candidate in an
isolated consumer and publish only after the owner merges, from clean `main`.
Do not republish `0.1.65`.

Related, and still true: the three-step rule in [`../../CLAUDE.md`](../../CLAUDE.md)
— bump `version` **in the same commit as the change**, `npm publish` from a clean
`main`, and `pnpm update arxatec-ui` in the consumer.
