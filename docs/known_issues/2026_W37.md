## `arxatec-ui@0.1.65` is published on npm and does not exist in git

> **Historical provenance unresolved** · registry `0.1.74`, base `main` `0.1.74`, security candidate `0.1.75`
> **Detected:** 2026-09-08 · **Last verified:** 2026-10-17 against base `main` (`d9cbd05`), all available git refs and the npm registry

Original observations on 2026-09-08:

```bash
npm view arxatec-ui version      # 0.1.65
grep '"version"' package.json    # 0.1.64   (main, and every one of the 8 remote branches)
```

At detection, `arxatec-lawyer-platform` declared `arxatec-ui: ^0.1.65` and locked
`0.1.65` with an integrity hash. Reverification on 2026-10-17 confirms that
`npm view arxatec-ui@0.1.65 version dist.tarball` still returns that published
tarball, while `git log --all -S '"version": "0.1.65"' -- package.json` finds no
producing commit. This is a historical provenance issue: registry latest and
current main are `0.1.74`; PR #22 prepares security candidate `0.1.75`.

Why it matters: a published version with no commit cannot be reviewed, cannot
be reverted by pointing at a tag, and cannot be diffed against what the consumer
is running.

The historical tarball provenance still needs investigation. For the next
release, review the diff from current main `d9cbd05` (`0.1.74`), validate the
packed `0.1.75` candidate in an isolated consumer and publish only after the
owner merges, from clean `main`.
Do not republish `0.1.65`.

Related, and still true: the three-step rule in [`../../CLAUDE.md`](../../CLAUDE.md)
— bump `version` **in the same commit as the change**, `npm publish` from a clean
`main`, and `pnpm update arxatec-ui` in the consumer.
