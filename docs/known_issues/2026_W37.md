## `arxatec-ui@0.1.65` is published on npm and does not exist in git

> **Live** · the platform already consumes it; nothing in this repo produces it
> **Detected:** 2026-09-08 · **Last verified:** 2026-09-08 against `main` (`046f7d2`) and against the npm registry

Measured today:

```bash
npm view arxatec-ui version      # 0.1.65
grep '"version"' package.json    # 0.1.64   (main, and every one of the 8 remote branches)
```

`arxatec-lawyer-platform` declares `arxatec-ui: ^0.1.65` and its `pnpm-lock.yaml`
is pinned to `0.1.65` with a real integrity hash, so the published tarball exists
and is in use. **What does not exist is the commit that produced it**: no branch in
this repo carries `0.1.65`.

Why it matters: this repo has no tests, and its only safety net is reading the
code and Storybook. A published version with no commit cannot be reviewed, cannot
be reverted by pointing at a tag, and cannot be diffed against what the consumer
is running.

What to do before publishing anything else: find out what went into `0.1.65` and
land it, or bump straight past it after confirming the tarball's content against
`main`. Do **not** publish `0.1.65` again — a published number is immutable.

Related, and still true: the three-step rule in [`../../CLAUDE.md`](../../CLAUDE.md)
— bump `version` **in the same commit as the change**, `npm publish` from a clean
`main`, and `pnpm update arxatec-ui` in the consumer.
