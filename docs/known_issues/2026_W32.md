- `src/hooks/use_media_query/index.ts:9` — synchronous `setMatches` in the effect
  body (`react-hooks/set-state-in-effect`). It is a shared hook, so the render
  cascade is paid by every consumer.

By rule: `set-state-in-effect` ×8, `immutability` ×2, and one each of
`only-export-components`, `rules-of-hooks`, `refs`, `purity`,
`incompatible-library`, `exhaustive-deps`.

Why it matters more here than in an app: **this is a package published to npm**. A
defect is not fixed by deploying, it is fixed by publishing a version and waiting
for the consumer to update.

## Two lockfiles coexist, and the npm one no longer installs

> **Live** · this is **D-2**, and since 2026-09-01 it is no longer symmetric
> **Detected:** 2026-08-04 · **Last verified:** 2026-09-01 against `a6d0c29`
> Full evidence: `git show 046f7d2:docs/registro/2026-09-01/NPM_ROTO_Y_REGLA_DE_VERSION.md`

The repo carries `package-lock.json` **and** `pnpm-lock.yaml`. Each can resolve a
different dependency tree, so "it works on my machine" depends on which one you
installed with.

What changed on 2026-09-01 is that they are no longer two equivalent options:

```text
$ npm ci        → ERESOLVE
$ npm install   → ERESOLVE
  @tiptap/extension-table@3.22.5 requires @tiptap/core@3.22.5 exactly,
  and the tree resolves @tiptap/core@3.22.4
$ pnpm install --frozen-lockfile   ✅
```

**The conflict is in `package.json`, not just in the lockfile**: the 28 tiptap
packages are declared with loose ranges (`^3.14.0`, `^3.22.4`) while their
sub-packages pin the `@tiptap/core` peer to an exact version. npm picks the newest
of each on its own and puts them out of step.

So: **install with `pnpm`**; everything else (the README scripts,
`prepublishOnly`, `npm publish`) stays npm. Removing `package-lock.json` is the
owner's call and is why this is still open rather than fixed.

Fixing the tiptap mismatch means pinning 28 packages to a coherent version, which
changes the tree of a library with no tests. That is separate work → `../BACKLOG.md`.
